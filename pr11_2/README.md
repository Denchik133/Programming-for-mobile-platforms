# Практична робота №11 (частина 2) — JWT-авторизація

**Варіант:** 1 — система авторизації з JWT  
**Дисципліна:** Програмування для мобільних платформ  
**Тема:** Dio, interceptors, авторизація та захист маршрутів

## Опис проєкту

`pr11_2` — Flutter-застосунок, який демонструє реєстрацію та вхід користувача, роботу з JWT access і refresh токенами та доступ до захищеного профілю. Після входу можна змінити ім’я й email, змінити пароль, перевірити автоматичне оновлення токена та вийти з облікового запису.

Для повторюваної роботи без зовнішніх ключів і доступності стороннього сервера застосунок використовує локальний демонстраційний mock auth API. Запити формуються через Dio, а mock-сервер відповідає на них у Dio interceptor. Такий сервер призначений для навчальної демонстрації, а не для розгортання у виробничому середовищі.

## Мета роботи

Мета — опрацювати розширену мережеву взаємодію у Flutter: налаштування Dio, request/response interceptors, централізовану обробку `DioException`, JWT-авторизацію, зберігання токенів і керування станом через Provider.

## Використані технології

- **Dart і Flutter** — мова та фреймворк застосунку.
- **Material 3** — компоненти інтерфейсу.
- **`dio` 5.11.1** — HTTP-клієнт, конфігурація тайм-аутів і ланцюжок interceptors.
- **`provider` 6.1.5+1** — передавання `AuthController` та оновлення UI.
- **`flutter_secure_storage` 11.2.0** — збереження сесії та даних локального mock-сервера у захищеному сховищі платформи.
- **`crypto` 3.0.8** — HMAC-SHA256 для демонстраційних JWT і SHA-256 для хешу пароля mock-акаунта.
- **`pretty_dio_logger` 1.4.0** — журналювання запитів у debug-режимі без виведення заголовків і тіл із токенами або паролями.
- **`flutter_test`** — автоматизовані тести API та поведінки авторизації.

## Функціональні можливості

- Реєстрація з перевіркою імені, email, пароля та його підтвердження.
- Вхід до акаунта з прапорцем «Запам’ятати мене».
- Демо-акаунт: `demo@pr11.local`, пароль `Flutter123`.
- Збереження access і refresh токенів у захищеному сховищі та автоматичне відновлення сесії після повторного запуску.
- Автоматичне додавання `Authorization: Bearer ...` до захищених запитів.
- Оновлення токенів після відповіді 401 і повтор початкового запиту.
- Перегляд та редагування профілю через захищені `GET /user` і `PUT /user`.
- Зміна пароля через захищений `POST /user/change-password`.
- Вихід з очищенням сесії та автоматичне завершення сесії після 10 хвилин бездіяльності.
- Кнопка «Перевірити оновлення JWT», яка навмисно створює відповідь 401 для демонстрації refresh і повторного запиту.
- Стани завантаження, повідомлення про помилки та валідація форм.

## Архітектура та реалізація

`main.dart` створює сховище, `TokenStorage`, локальний mock-сервер, Dio-клієнт та `AuthApi`, а `ChangeNotifierProvider` передає `AuthController` екранам. `AuthGate` показує індикатор початкового завантаження, форму входу або захищений профіль відповідно до стану авторизації.

`createAuthDio` задає базові параметри Dio: тайм-аути надсилання, з’єднання й отримання відповіді по 10 секунд, а також `validateStatus` для обробки статусів нижче 500. До Dio додаються JWT, error, logging і mock-server interceptors. JWT interceptor додає access token до захищеного запиту. Якщо захищений маршрут відповідає 401, interceptor надсилає refresh token, зберігає нову пару токенів і один раз повторює початковий запит. Паралельні refresh-запити використовують спільну операцію оновлення.

Локальний mock-сервер реалізує маршрути реєстрації, входу, оновлення токенів і роботи з профілем. Він підписує навчальні JWT алгоритмом HS256, перевіряє строк дії та версію refresh token, а після оновлення змінює версію, щоб попередній refresh token не можна було використати повторно. Кнопка демонстрації refresh навмисно повертає 401 для наступного запиту профілю.

Access і refresh токени, а також записи локальних демо-акаунтів зберігаються через `flutter_secure_storage`; пароль акаунта зберігається як хеш. На macOS застосовано Keychain у режимі без Data Protection Keychain, щоб для навчальної збірки не вимагати Keychain Sharing entitlement. Неактивність вимірюється таймером, який поновлюється під час натискання в захищеній частині інтерфейсу.

**Обмеження демонстраційного сервера:** mock-сервер, його тестовий ключ підпису JWT і дані акаунтів працюють у межах клієнтського застосунку. Ця схема показує послідовність Dio-запитів і interceptor-ів, але не замінює серверну авторизацію. У реальному сервісі ключ підпису та перевірка паролів мають залишатися на сервері, а паролі — оброблятися спеціалізованим адаптивним алгоритмом хешування.

## Встановлення та запуск

Потрібні Flutter SDK і Dart SDK. Зовнішній API ключ та доступ до інтернету для демонстрації не потрібні: запити обробляє локальний mock auth API.

У терміналі з каталогу `pr11_2` виконайте:

```bash
flutter pub get
flutter devices
```

Запуск desktop-застосунку на macOS:

```bash
flutter run -d macos
```

Запуск на підключеному пристрої або запущеному емуляторі (підставте ID зі списку `flutter devices`):

```bash
flutter run -d <device_id>
```

Для перевірки коду й тестів:

```bash
flutter analyze
flutter test
```

## Тестування

Тести використовують `MemorySecureKeyValueStore` і той самий Dio interceptor-chain із локальним mock-сервером. Перевіряються реєстрація та формат JWT, помилка входу, автоматичний refresh після 401 із повтором запиту, відновлення збереженої сесії, редагування профілю, зміна пароля, відповіді 404 і 500, а також завершення сесії після тайм-ауту бездіяльності.

Результати перевірки:

- `flutter analyze` — проблем не знайдено;
- `flutter test` — усі 7 тестів пройшли;
- `flutter build macos` — застосунок успішно зібрано;
- `flutter build apk --debug` — Android-застосунок успішно зібрано.

## Висновки

Створено демонстраційний Flutter-застосунок із реєстрацією, входом, захищеним профілем, ротацією JWT refresh-токенів та автоматичним виходом після бездіяльності. У роботі опрацьовано Dio, interceptors, Provider, захищене сховище, обробку помилок і тестування мережевого шару на локальному mock API.
