# Практична робота №11 (Частина 1) — HTTP-запити та REST API

## Варіант 4. TODO-менеджер

### 1. Опис проєкту

`pr11` — Flutter-застосунок для перегляду та керування списком завдань. Він отримує завдання й користувачів із JSONPlaceholder, відображає їх у зручному списку та демонструє основні HTTP-операції REST API.

Обрано варіант 4, оскільки ресурс завдань має просту модель (`id`, `userId`, `title`, `completed`) і не потребує карт, зображень, коментарів або окремого сервера.

### 2. Мета роботи

Мета — навчитися надсилати HTTP-запити з Flutter, перетворювати JSON-відповіді на моделі, показувати асинхронні стани й обробляти помилки мережі. У роботі відпрацьовано `GET`, `POST`, `PUT`, `PATCH` і `DELETE`.

### 3. Технології

- **Dart і Flutter** — мова та фреймворк застосунку;
- **Material 3** — компоненти інтерфейсу;
- **`http` 1.6.0** — HTTP-клієнт;
- **JSONPlaceholder** — тестовий REST API;
- **`flutter_test` і `MockClient`** — автоматичні тести моделей та HTTP-сервісу.

### 4. Функціональні можливості

- завантаження завдань через `GET /todos` і користувачів через `GET /users`;
- завантаження завдань обраного користувача через `GET /todos?userId={id}`;
- створення завдання з назвою, користувачем і початковим статусом (`POST`);
- редагування назви завдання (`PUT`);
- перемикання статусу «виконано» (`PATCH`);
- видалення зі свайпом, підтвердженням і можливістю скасувати дію протягом трьох секунд (`DELETE`);
- пошук за назвою, фільтри «Усі», «Виконані», «Очікують» і фільтр за користувачем;
- групування списку за користувачами та показ загальної кількості, виконаних і невиконаних завдань із progress bar;
- pull-to-refresh, індикатор завантаження, порожній стан і повторний запит після помилки.

```text
│   │   └── todo_list_screen.dart

│   ├── api_service_test.dart
│   └── models_test.dart
├── pubspec.yaml

```

`Todo` та `User` описують дані й мають методи `fromJson()` та `toJson()`. `ApiService` містить HTTP-запити, JSON-парсинг і перетворення помилок на `ApiException`. `TodoListScreen` завантажує дані, показує список і керує фільтрами. `TodoFormScreen` створює або редагує завдання. Невеликі компоненти інтерфейсу для картки, прогресу, порожнього стану й помилки оголошені в `todo_list_screen.dart`.

### 6. Архітектура та реалізація

Початкове завантаження виконується через `FutureBuilder`: паралельно надсилаються запити за завданнями й користувачами. Під час очікування показується `CircularProgressIndicator`; якщо запит завершується помилкою, інтерфейс показує повідомлення та кнопку повторної спроби.

Екран передає запити до `ApiService`, а не формує HTTP-виклики всередині віджетів. Сервіс використовує `http.Client`, який можна підмінити в тестах. Для кожного запиту встановлено таймаут 10 секунд. Обробляються відсутність мережі, таймаут, HTTP 404, помилки сервера 500+, інші неуспішні статуси та некоректний JSON.

Для завершеного завдання надсилається `PATCH` лише зі зміненим полем `completed`; редагування назви надсилає повний об’єкт через `PUT`. Видалення спершу проходить підтвердження, а після успішної відповіді елемент можна повернути локально через snackbar протягом трьох секунд.

**Обмеження тестового API:** JSONPlaceholder імітує відповіді на `POST`, `PUT`, `PATCH` і `DELETE`, але не зберігає ці зміни на сервері. Тому додані завдання та зміни, включно зі скасуванням видалення, відображаються в інтерфейсі лише протягом поточного сеансу. Для локально створених записів наступні зміни підтримуються у стані клієнта.

### 7. Встановлення, запуск і перевірка

Потрібен встановлений Flutter SDK і доступ до інтернету. На Android застосунку потрібен дозвіл `INTERNET`, він доданий у `android/app/src/main/AndroidManifest.xml`. Для macOS у Debug і Release entitlements задано `com.apple.security.network.client`, щоб sandbox дозволяв вихідні запити до API. Інші спеціальні змінні середовища не потрібні.

У терміналі з каталогу `pr11` виконайте:

```bash
flutter pub get
flutter run
```

Щоб переглянути доступні пристрої та вибрати конкретний:

```bash
flutter devices
flutter run -d <device_id>
```

Для запуску на macOS:

```bash
flutter run -d macos
```

Команди перевірки:

```bash
flutter analyze
flutter test
```

### 8. Тестування

Автоматичні тести перевіряють JSON-моделі, GET із фільтром користувача, HTTP-методи POST/PUT/PATCH/DELETE, а також помилки 404, 500, offline, timeout і некоректний JSON. Запити у тестах ізольовані через `MockClient`, тож тести не залежать від зовнішньої мережі.

Результати перевірки проєкту:

- `flutter test` — усі 10 тестів пройшли;
- `flutter analyze` — проблем не знайдено;
- `flutter build macos` — застосунок успішно зібрано;
- `flutter build apk --debug` — Android-застосунок успішно зібрано.
